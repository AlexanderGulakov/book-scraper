# OLX watcher

Стежить за сторінками пошуку на **olx.ua** і надсилає в **Telegram** (опційно — на e-mail),
коли з'явилось нове оголошення або подешевшало вже відоме.

Повністю безкоштовно: GitHub Actions як планувальник, Telegram Bot API як канал сповіщень,
MongoDB Atlas (безкоштовний M0, 512 МБ) як база стану. Жодного сервера, жодної карти.

---

## Як воно працює

OLX рендерить результати пошуку на сервері й вкладає їх у HTML сторінки як
`window.__PRERENDERED_STATE__`. Тому не потрібен ні headless-браузер, ні приватний API —
достатньо одного GET-запиту й `json.loads`. Звідти беруться id, заголовок, ціна, валюта,
місто, стан, дата створення і фото.

Раз на N хвилин workflow:

1. качає першу сторінку кожного пошуку зі списку;
2. відкидає те, що не проходить фільтри (ключові слова, місто, «просунуті» оголошення);
3. порівнює зі станом у базі:
   - **id, якого не було** + ціна ≤ `max_price` → «нове оголошення»;
   - **ціна впала** щонайменше на `min_drop_percent` і тепер ≤ `max_price` → «ціна впала»;
4. шле повідомлення в Telegram;
5. записує в Mongo лише те, що змінилось (див. «Стан у MongoDB»).

Перший запуск кожного нового пошуку **мовчазний** — він лише запам'ятовує те, що вже висить
на OLX, щоб не прилетіло 40 повідомлень одразу. Сповіщення починаються з другого запуску.

## Налаштування за 10 хвилин

### 1. Telegram-бот

1. Напишіть [@BotFather](https://t.me/BotFather) → `/newbot` → отримаєте токен виду
   `8123456789:AAH...`.
2. Напишіть своєму боту будь-що (`/start`) — інакше він не має права вам писати.
3. Дізнайтесь свій `chat_id`: відкрийте
   `https://api.telegram.org/bot<ВАШ_ТОКЕН>/getUpdates` — потрібне число в `"chat":{"id":...}`.

### 2. Репозиторій

Створіть репозиторій на GitHub і залийте туди вміст цієї теки.

> **Робіть репозиторій публічним.** Для публічних репо хвилини GitHub Actions безлімітні,
> для приватних — 2000 хв/міс, а запуск щочверть години з'їдає ~2880 хв. У коді немає
> нічого приватного: токени лежать у Secrets, а `watches.yaml` — це просто ваші пошукові
> посилання. Якщо репо все ж має бути приватним — ставте cron `0 * * * *` (раз на годину,
> ~720 хв/міс) або тримайте джобу на своєму ПК (див. нижче).

### 3. Secrets

**Settings → Secrets and variables → Actions → New repository secret**:

| Ім'я | Значення |
|---|---|
| `TELEGRAM_BOT_TOKEN` | токен від BotFather |
| `TELEGRAM_CHAT_ID` | ваш chat id |
| `MONGODB_URI` | рядок підключення до Atlas — див. «Стан у MongoDB» |
| `BOOKFLEA_COOKIE` | необов'язково: значення кукі `accessToken` з bookflea.co |
| `BOOKFLEA_EMAIL` / `BOOKFLEA_PASSWORD` | необов'язково: щоб бот сам логінився, коли кукі протухне |

⚠ Букфлі **не працює з GitHub Actions** — сайт вибирає каталог за IP, і з США
віддає польський. Цей watch крутиться вдома, див. «Букфлі вдома».

Необов'язково, якщо хочете ще й пошту (Gmail вимагає [App Password](https://myaccount.google.com/apppasswords), не звичайний пароль):
`SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`, `SMTP_TO`.

### 4. Дозволи

Нічого вмикати не треба: стан живе в Mongo, тож воркфлоу більше не пише в репо
(`permissions: contents: read`). Якщо колись раніше вмикали «Read and write
permissions» — тепер це можна вимкнути.

### 5. Перший запуск

**Actions → OLX watch → Run workflow**. Перевірте лог: має бути
`перший запуск: запам'ятав N оголошень`. Натисніть ще раз — тепер бот писатиме про зміни.

## Конфіг `watches.yaml`

```yaml
defaults:
  currency: UAH
  pages: 1
  min_drop_percent: 3

watches:
  - name: "Фундація (Азімов)"
    url: "https://www.olx.ua/uk/hobbi-otdyh-i-sport/knigi-zhurnaly/q-фундація/?currency=UAH&search%5Border%5D=created_at%3Adesc"
    max_price: 600
    exclude_keywords: ["копія", "репринт"]
```

| Параметр | Що робить |
|---|---|
| `url` | сторінка пошуку OLX. Найпростіше: налаштуйте фільтри на сайті руками й скопіюйте адресу. Додайте сортування «від найновіших». |
| `max_price` / `min_price` | межі ціни. Без `max_price` сповіщення прилітають про все нове. |
| `max_price_bundle` | окрема межа для комплектів: за кілька книжок логічно платити більше |
| `bundle_keywords` | слова-ознаки комплекту («комплект», «набір»). Комплект також розпізнається, коли ключове слово повторюється в заголовку: «Служниця спостерігає, Весілля служниці» — дві згадки, дві книжки |
| `currency` | ціни в іншій валюті ігноруються (щоб 100 $ не зійшло за «дешевше 600») |
| `include_keywords` | має збігтися хоча б одне слово в заголовку |
| `exclude_keywords` | жодне з цих слів не має бути в заголовку |
| `cities` | напр. `["Київ", "Львів"]` |
| `skip_promoted` | `true` — ігнорувати платно підняті оголошення |
| `allow_no_price` | `true` — сповіщати й про «Обмін»/«Договірна» |
| `min_drop_percent` | поріг падіння ціни у %, щоб не смикало на 10 грн |
| `pages` | скільки сторінок читати; при сортуванні за датою 1 вистачає |
| `prune_days` | забути оголошення, яких не бачили N днів (щоб `state.json` не ріс вічно) |
| `enabled: false` | тимчасово вимкнути пошук |

### Звіт про зняті оголошення

Раз на годину бот перевіряє оголошення, які зникли з видачі, і звітує про ті,
яких уже немає на сайті:

```
🧾 Зняті з продажу за годину — 3 шт.

Служниця (Мак-Фадден)
• 170 грн · 2 дн. — Книга «Служниця»
• 250 грн · 9 дн. — Служниця спостерігає
• 900 грн · 41 дн. ⏳ — Книга оповідь служниці

Медіана: 250 грн (від 170 до 900)
Провисіли: медіана 9 дн., від 2 дн. до 41 дн.
```

Це сировина для аналітики цін (див. нижче). Історія накопичується в колекції
`soldListings` (останні 60 днів), і саме на ній рахуються медіани.

**Як це працює і чого варте.** Зникнення з першої сторінки пошуку нічого не
означає — свіжі оголошення просто виштовхують старі вниз. Тому кожен зниклий
запис перевіряється за власним посиланням: живе віддає HTTP 200 і
`status: active`, зняте — **HTTP 410**. Текст сторінки для цього не годиться:
слова «видалено» і «404» лежать у локалізації й присутні навіть на живій.

⚠ **Зняли ≠ продали.** Продавець міг передумати, а приблизно через 30 днів OLX
сам архівує неоновлені оголошення. Тому все, що провисіло понад 30 днів,
позначається ⏳ — такі записи для статистики ненадійні.

Скільки пролежало — рахується від дати створення оголошення (OLX віддає її
у видачі) до моменту, коли ми помітили зникнення. Похибка — до години.

| Параметр (у `defaults`) | Що робить |
|---|---|
| `sold_report_minutes` | як часто звітувати; `0` вимикає звіт |
| `sold_report_max_checks` | скільки посилань перевіряти за один звіт (кожне — окремий запит) |
| `sold_check_max_age_days` | оголошення старші за стільки днів у чергу перевірок не беруться |

**Чому є межа віку.** Черга сортується «найдавніше зниклі першими», тож без
цього фільтра всі перевірки за прогін діставались двотижневим лежням, а свіжі
оголошення — ті, чиє зникнення справді схоже на продаж, — чекали своєї черги
годинами. Для статистики довгожителі не губляться: аналітика бачить їх з
іншого боку, як тих, що лежать.

Букфлі поки не охоплений: перевірка написана під розмітку OLX.

### Аналітика цін: за скільки беруть і з якої ціни не рухається

Раз на добу (о `daily_report_at`, за замовчуванням **03:45** за Києвом) приходить один звіт:

```
📊 Скільки за що дають · 21.09
За 30 дн. зникло 137 оголошень · висять понад 14 дн. 292

━━ Розходяться ━━

Мак-Фадден: Служниця
🟢 до 330 · 🙂 до 430 · 🔴 від 620
12 шт. · зникали за 2 дн. · 9 лежать

━━ Не рухається зовсім ━━
за час спостережень не зникло жодного; стоп-ціна — з якої точно ні
🔴 Лоліта (Набоков) — 17 лежать, стоп-ціна 230
```

Ті самі числа підписують кожне сповіщення про оголошення — рядком під ціною:
**🟢 Брати не думаючи**, **🙂 Непогана ціна**, **🔴 Задорого**,
**🤷 Не вдалося визначити**.

**Дві вибірки, два різні питання.** «Продані» — оголошення, які зникли з сайту
(їх дає щогодинна перевірка вище). «Довгожителі» — оголошення, які **все ще у
видачі** і висять довше за `stalled_days`. Друга множина і є відповіддю на «з
якої ціни не рухається взагалі».

**Найтонше місце — межа «задорого».** Наївний перцентиль довгожителів дає
нісенітницю: у Гаррі Поттера половина дешевих оголошень висить тижнями просто
тому, що їх там сотні, і межа виходила *нижчою* за ціни, за якими книжки
демонстративно продавались («нормально до 675, але з 248 не рухається»). Тому:

- **є продажі** — мертвою зоною вважається лише те, що лежить **вище** за 75-й
  перцентиль проданих. Нижче цієї позначки лежання нічого не доводить;
- **продажів нема** — береться 25-й перцентиль усіх довгожителів, і це вже
  інше твердження: «навіть за стільки не беруть». У звіті воно стоїть в
  окремому блоці, щоб здогад не видавався за висновок.

Сказати «беріть» без жодного продажу нема на чому, тому там вердикт може бути
лише 🔴 або 🤷 — ніколи 🟢.

**Каталог книг (`books:` у `watches.yaml`).** Статистику треба рахувати по
книжці, а не по пошуку: у watch «Гаррі Поттер» лежить і один том за 150 грн,
і семитомник за 6500, і медіана по такій купі не описує жодного реального
оголошення. Позиції перебираються **згори вниз, перший збіг виграє**, тож
конкретніші («Колонія + Колапс») мають стояти вище за загальніші («Колонія»).
Не збіглось нічого — книгою вважається назва watch'а; так і задумано для
пошуків, де книжка й так одна (Кінг, Клер). Комплекти завжди їдуть в окрему
позицію `<назва> · комплект`.

Що відсіюється зі статистики окремо від звичайних фільтрів:

- **російськомовні видання** — за літерами `ы ъ э ё` і російськими написаннями
  назв («Гарри Поттер», «Код да Винчи»). Свідомо асиметрично: краще втратити
  кілька українських оголошень, ніж отримати систематичний зсув униз;
- **гуртові лоти** чужих книжок («41 шт. Частина 3» за 7300 грн);
- ціни поза межами watch'а (`max_price`) і дешевші за `analytics_min_price`.

Одне оголошення — одне спостереження: пошуки навмисне перетинаються, і без
дедуплікації три watch'і робили з п'яти оголошень п'ятнадцять.

| Параметр (у `defaults`) | Що робить |
|---|---|
| `analytics_enabled` | `false` — вимкнути і звіт, і вердикти |
| `daily_report_at` | коли слати звіт, `"ГГ:ХХ"` за Києвом; `false` вимикає |
| `daily_report_hour` | старий вигляд тієї ж настройки (лише година), досі працює |
| `analytics_window_days` | глибина історії проданих |
| `stalled_days` | з якого віку оголошення вважається «лежить» |
| `stalled_seen_hours` | і воно має бути у видачі не давніше ніж стільки годин |
| `sold_max_age_days` | знято пізніше — радше архів OLX, ніж продаж |
| `min_sold` / `min_stalled` | менше спостережень — «не вдалося визначити» |
| `analytics_min_price` | дешевше — сміття, у статистику не йде |
| `report_max_books` | скільки позицій влазить в одне повідомлення |

Розклад GitHub Actions пливе, тож звіт їде **з першим прогоном після**
вказаного часу, а не рівно о ньому. Позначка «за сьогодні вже слали» —
`state["book_report_date"]`.

⚠ Три застереження, які варто тримати в голові: «знято» ≠ «продано»; ціна в
оголошенні ≠ ціна угоди (торгу ми не бачимо); вибірка мала, і поки вона мала,
чесна відповідь — 🤷.

### Друге джерело: bookflea.co

```yaml
  - name: "Букфлі"
    source: bookflea
    mode: latest          # один запит за найновішими page_size оголошень
    page_size: 48
    use_default_excludes: false
    keywords: [Відьмак, Ден Браун, Кідрук, Гаррі Поттер]
```

| Параметр | Що робить |
|---|---|
| `source: bookflea` | замість `url` тут `keywords` — список слів |
| `mode: latest` | **один** запит на стрічку найновіших; збіги шукаються локально |
| `mode: search` | окремий запит на кожне слово: бачить увесь каталог (2400+), але це 9 запитів — ставте до нього `interval_minutes: 60` |
| `page_size` | скільки найновіших читати. 48 покриває понад добу при темпі ~2 книжки/год |
| `interval_minutes` | не перевіряти частіше, ніж раз на N хвилин (працює для будь-якого watch) |

Ключове слово шукається і в назві, і в **авторі**, без урахування регістру й
типу апострофа. Власний пошук сайту нечіткий (на «Бункер» віддає «Альманах
Сталкер»), тому в `mode: search` його результати додатково перевіряються
локально.

#### Чому Букфлі не можна крутити з GitHub Actions

Букфлі — це кілька окремих ринків за країнами (Україна, Польща, Німеччина).
Яку країну ви бачите, вирішує **IP клієнта**, а раннер GitHub Actions стоїть у
США — тому звідти бот бачить **польський** каталог: інші оголошення, ціни в
злотих, нуль корисних збігів. Перевірено 2026-09-17: з України пошук по дев'яти
словах дає 45 кандидатів, з Actions — 12, і **жоден id не збігається**.

Не працює нічого з цього (теж перевірено): параметри `?country=UA`, шлях
`/ua/search`, заголовки `x-vercel-ip-country` / `cf-ipcountry` /
`accept-language`, **і навіть авторизована сесія** — залогінений раннер бачить
той самий польський каталог, а з України залогінена й анонімна видача
побайтово однакові.

Лишається один шлях: **питати Букфлі з українського IP**. Тому цей watch
крутиться не в хмарі, а вдома — див. «Букфлі вдома» нижче.

#### Авторизація (є в коді, каталог не змінює)

Може знадобитись, якщо сайт колись почне ховати щось від анонімів. Сесія
тримається на одній кукі `accessToken`, яка живе близько місяця:

- `BOOKFLEA_COOKIE` — значення цієї кукі (DevTools → Application → Cookies →
  `bookflea.co` → `accessToken`). Приймається і голе значення, і повний рядок
  заголовка `Cookie`.
- `BOOKFLEA_EMAIL` + `BOOKFLEA_PASSWORD` — запасний шлях: якщо кукі протухла,
  бот сам робить `POST /api/auth/login`.

Спершу пробується кукі (перевірка одним запитом на `/me`), логін — лише коли
вона мертва. Якщо в токені читається дата (це JWT), за тиждень до кінця
прилетить нагадування оновити секрет — один раз, а не щопрогону. Кукі
прив'язана до домену Букфлі й ніколи не їде на OLX, хоч сесія й спільна.

Якщо у видачі трапиться не та валюта, бот один раз напише про це в Telegram і
не надішле такі оголошення: `55 zł` — це не `55 грн`.

У режимі `latest` видно лише вікно найновіших, тому падіння ціни ловиться,
поки оголошення з нього не випало. Якщо між перевірками стрічка провернулась
цілком, бот надішле попередження — це сигнал збільшити `page_size`.

Інтервал змінюється в `.github/workflows/watch.yml`, рядок `cron`. Мінімум, який приймає
GitHub, — 5 хвилин, але реально розклад «пливе»: буває 15–40 хв затримки, особливо в
години пік. Для полювання за рідкісними книжками цього вистачає.

## Стан у MongoDB

Раніше стан жив у `state.json`, який Actions комітив назад у репо, а домашня
машина тримала свій окремий `state.local.json`. Це давало три болі: коміт на
кожен прогін в історії, гонки `git pull --rebase`, і дві половини стану, які
ніколи не бачать одна одну — аналітика цін удома не знала нічого про OLX, а в
хмарі не знала про Букфлі.

Ключова умова переїзду: **писати документами, а не файлом**. Якщо класти весь
стан одним документом, вийде той самий `state.json`, тільки в хмарі, з тими
самими гонками. Тому `storage.MongoStore.save()` порівнює поточний стан зі
знімком, зробленим при читанні, і пише лише різницю. Типовий прогін торкається
одиниць документів; два писачі торкаються різних і не конфліктують.

| колекція | `_id` | що всередині |
|---|---|---|
| `watcherState` | `"watcher"` | `version`, `lastBookReportDate`, `lastSoldReportAt` |
| `watches` | ключ watch'а | `isSeeded`, `lastRunAt`, `lastHeartbeatAt`, `recentAdIds` |
| `ads` | `{watch, adId}` | `price`, `currency`, `title`, `url`, `firstSeenAt`, `lastSeenAt`, `missingSinceAt` |
| `soldListings` | `{watch, adId, goneAt}` | те саме + `daysListed` |
| `priceHistory` | `{adId, seenAt}` | `price`, `currency`, `title` на момент спостереження |

`_id` складений, а не рядок із роздільником: назви watch'ів довільні
(«Клер: Місто скла»), і будь-який роздільник рано чи пізно трапиться всередині
назви. `watch` і `adId` дублюються на верхньому рівні документа навмисно — щоб
запит писався як `{watch: "Букфлі"}`, а не `{"_id.watch": "Букфлі"}`.

### Імена в базі і в пам'яті різні — це навмисно

У пам'яті поля лишились історичними й куцими (`cur`, `seen`, `miss`, `first`):
на них спираються `main.py` і `analytics.py`, і перейменовувати їх означало б
чіпати півпроєкту заради косметики. У базі ж на ці документи дивиться людина —
через Compass, Studio 3T чи Browse Collections в Atlas, — тому там імена повні
та camelCase.

Переклад робить `storage.py` за таблицями `AD_FIELDS` / `WATCH_FIELDS` /
`SOLD_FIELDS` / `STATE_FIELDS`. Поля, яких у таблиці немає, проходять як є: нове
поле в `main.py` потрапить у базу під своїм іменем, а не зникне (є тест).

| у пам'яті | у базі |
|---|---|
| `cur` | `currency` |
| `seen` | `lastSeenAt` |
| `first` | `firstSeenAt` |
| `miss` | `missingSinceAt` |
| `created` | `createdAt` |
| `seeded` | `isSeeded` |
| `last_run` | `lastRunAt` |
| `heartbeat_last` | `lastHeartbeatAt` |
| `window` | `recentAdIds` |
| `id` (у `sold`) | `adId` |
| `days` | `daysListed` |
| `gone` | `goneAt` |
| `book_report_date` | `lastBookReportDate` |
| `sold_report_last` | `lastSoldReportAt` |

`priceHistory` — єдине, чого у файловому стані не існувало. Файл тримав лише
останній зріз: побачили нову ціну — стару затерли. Тому аналітика вміла сказати
«за скільки зняли», але не «як ця книжка дешевшала». Тепер на кожну зміну ціни
пишеться рядок, і він переживає саме оголошення.

### Налаштування Atlas

1. [cloud.mongodb.com](https://cloud.mongodb.com) → безкоштовний кластер **M0**
   (512 МБ, без картки). Регіон — найближчий, напр. Frankfurt.
2. **Database Access** → новий користувач. Пароль хай буде лише з букв і цифр:
   спецсимволи в рядку підключення треба percent-encode'ити (`@` → `%40`), і це
   найчастіша причина «чомусь не підключається».
3. **Network Access** → `0.0.0.0/0`. Раннер GitHub Actions щоразу бере новий IP
   з діапазонів Azure, вайтлистити їх неможливо. Захист лишається на паролі та
   TLS; якщо це муляє — є [Allow MongoDB Atlas IP](https://github.com/marketplace/actions/allow-mongodb-atlas-ip),
   який додає IP раннера перед кроком і прибирає після (крок прибирання
   обов'язково з `if: always()`, інакше після впалого прогону запис лишиться).
4. **Connect → Drivers → Python** → скопіювати рядок.
5. Покласти його в **двох** місцях, однаковий:
   - GitHub → Settings → Secrets and variables → Actions → `MONGODB_URI`;
   - `.env` поруч з `main.py` на домашній машині.

   Різні рядки = дві бази = рівно та проблема, від якої ми тікали.

### Міграція зі `state.json`

Робиться **один раз**, з домашньої машини — бо саме там лежить
`state.local.json`, якого в репозиторії немає.

```bash
py migrate_state.py --dry-run                    # порахувати, нічого не писати
py migrate_state.py state.json state.local.json  # перенести
```

Скрипт зводить обидва файли в одну базу (конфлікти — за свіжістю `seen` /
`last_run`), відмовляється писати в непорожню базу без `--force`, і після
запису читає все назад і звіряє.

Чому не «перший прогін сам наповнить базу»: порожня база для watcher'а означає
перший запуск, він мовчки засідить усе, що бачить, — і 79 записів історії
знятих, на яких тримається вся аналітика цін, зникнуть назавжди. Це єдине, чого
не можна перескрапити.

`state.json` після міграції лишається в репо як зліпок на всяк випадок; коли
переконаєтесь, що база працює — можна видалити.

## Локальний запуск

```bash
pip install -r requirements.txt

# подивитись, що знайшлося, нічого не надсилаючи
python main.py --dry-run

# з реальними сповіщеннями
export TELEGRAM_BOT_TOKEN=...
export TELEGRAM_CHAT_ID=...
python main.py

python main.py --reset      # забути побачені оголошення (історію НЕ чіпає)
python -m pytest -q         # тести
```

Де тримати стан, вирішує `--storage`:

| значення | що робить |
|---|---|
| `auto` (за замовч.) | Mongo, якщо є `MONGODB_URI`; інакше файл `--state` |
| `mongo` | лише Mongo; без URI або без зв'язку — падає з поясненням |
| `json` | лише файл, навіть якщо URI заданий |

У воркфлоу й у `run-bookflea.bat` стоїть саме `mongo`, а не `auto`, і це
навмисно: тихий відкат на файл означав би, що стан нікуди не зберігся, а
наступний прогін вважав би всі оголошення новими — сорок повідомлень у Telegram
замість помилки в логах.

`--reset` у базі чистить `watches` і `ads`, але **лишає** `soldListings` і
`priceHistory`. У файлі він зносив усе разом, бо файл перезаписувався
цілком; у базі так робити не можна — історію не перескрапиш.

### Букфлі вдома — Планувальник Windows

Букфлі потрібен український IP (чому — вище), тому він крутиться не в хмарі.
Робота ділиться ключами `--only` / `--skip`:

| де | команда |
|---|---|
| GitHub Actions | `python main.py --storage mongo --skip bookflea` |
| ваш ПК | `run-bookflea.bat` (усередині `--only bookflea --storage mongo`) |

`bookflea` — це значення `source`, тому ключі пишуться латиницею: кирилиця в
аргументах Планувальника й у YAML воркфлоу легко ламається на кодуваннях.

**Окремий `state.local.json` більше не потрібен.** Він існував тому, що двоє
писачів в один файл затирали одне одного. У Mongo кожен пише свої документи —
Actions чіпає watch'і OLX, домашній прогін чіпає Букфлі, — тож розділяти вже
нема чого. Побічний виграш: аналітика цін уперше бачить обидва джерела разом.
Старий файл нікуди не дівається, просто перестає використовуватись — перенесіть
його в базу (розділ «Міграція»), перш ніж видаляти.

Логін тут **не потрібен**: з українського IP сайт і так віддає український
каталог. `BOOKFLEA_COOKIE` та пароль потрібні були лише для спроби обійти
географію з хмари.

#### Разово

```
py -3 -m pip install -r requirements.txt
copy .env.example .env
notepad .env
```

Токен і `TELEGRAM_CHAT_ID` — у `.env`; він у `.gitignore` і в репозиторій не
потрапляє. Не знаєте chat_id — напишіть боту повідомлення й запустіть
`py -3 main.py --find-chat`.

⚠️ `setx` теж працює, але **змінна середовища має пріоритет над `.env`**:
якщо колись покладете значення обома способами, `.env` мовчки перестане
діяти, і буде `400 chat not found` при правильному файлі. Щось одне.
Перевірка, що все зібралось (нічого не надсилає):

```
py -3 main.py --only bookflea --storage mongo --dry-run
```

Створення завдання — **подвійний клік по `bookflea-install.bat`**. Він бере
шлях із власного розташування, перестворює завдання, якщо воно вже є, одразу
проганяє його й показує код останнього прогону.

⚠️ Не збирайте команду `schtasks` руками з цього README. Один раз її вже
скопіювали дослівно, разом із `<ви>` у шляху: завдання створилось, у
Планувальнику показувало `Ready`, справно «спрацьовувало» кожні 30 хвилин —
і щоразу падало з `0x1`, бо такого шляху не існує. Ні логів, ні сповіщень,
ні натяку на причину. Якщо все-таки робите вручну — підставте **свій**
шлях і перевірте результат:

```
schtasks /Query /TN "Bookflea watcher" /V /FO LIST | findstr /C:"Task To Run" /C:"Last Result"
```

`Last Result` має бути `0`. Будь-що інше — завдання не працює, скільки б
`Ready` не світилось поруч.

Перший справжній прогін мовчазний — він лише запам'ятовує те, що вже висить.
Пульс («живий, нічого нового») починається з другого.

#### Щодня

Нічого. Завдання спрацьовує саме, поки комп'ютер увімкнений і ви залогінені.
Якщо хочете вмикати вручну — `bookflea-on.bat` і `bookflea-off.bat` (подвійний
клік). `bookflea-off.bat` ще й перериває прогін, якщо він саме йде.

Те саме командою:

```
schtasks /Change /TN "Bookflea watcher" /ENABLE
schtasks /Change /TN "Bookflea watcher" /DISABLE
schtasks /Run    /TN "Bookflea watcher"      :: прогнати негайно, поза розкладом
schtasks /Query  /TN "Bookflea watcher" /V /FO LIST | findstr /C:"Status" /C:"Last Run"
schtasks /Delete /TN "Bookflea watcher" /F   :: прибрати зовсім
```

Що відбувалось — у `logs\bookflea.log`. Стан не губиться: після вимкнення й
увімкнення бот продовжує з того самого місця, повторів у Telegram не буде.

Той самий підхід годиться, якщо OLX колись почне різати запити з дата-центрів:
тоді вдома крутиться вже все, без `--only`.

Мінус — працює лише коли ПК увімкнений. Для книгарні, де оголошення висять
тижнями, пропуски дешеві.

## Якщо щось пішло не так

### `OLX відповів 403`

Найчастіша проблема. Причин рівно дві, і вони вимагають різних дій.

**1. TLS-відбиток.** Анти-бот дивиться не лише на заголовки, а й на те, як клієнт
встановлює TLS-з'єднання (JA3) і в якому порядку шле HTTP/2-фрейми. У Python-бібліотеки
`requests` цей відбиток впізнається миттєво. Лікується `curl_cffi`, який прикидається
справжнім Chrome на рівні TLS — він уже в `requirements.txt` і використовується за
замовчуванням.

**2. IP дата-центру.** GitHub Actions крутиться на адресах Azure, і частина сайтів ріже
весь цей діапазон незалежно від того, наскільки добре ви прикидаєтесь браузером. Тут
жоден код не допоможе.

Щоб зрозуміти, який саме випадок ваш, запустіть **Actions → OLX watch → Run workflow →
mode: `probe`**. Скрипт покаже ваш IP з назвою провайдера й перебере стратегії:

```
IP: 20.55.x.x  ·  AS8075 Microsoft Corporation  ·  US

стратегія                          результат
------------------------------------------------------------------
urllib (без нічого)                HTTP 403 · блокує: DataDome
requests + заголовки Chrome        HTTP 403 · блокує: DataDome
curl_cffi chrome131                OK ✅  3,151,557 байт, дані на місці

➜ Працює: OLX_BACKEND=curl_cffi OLX_IMPERSONATE=chrome131
```

Якщо якийсь рядок дав `OK ✅` — пропишіть цю комбінацію в **Settings → Secrets and
variables → Actions → Variables**: `OLX_BACKEND` і `OLX_IMPERSONATE`. Workflow їх підхопить.

Якщо **жодна** стратегія не пройшла, а в полі org видно хостинг — це блок за IP, і
залишається перенести джобу на домашній ПК (Планувальник Windows, див. вище) або на
[self-hosted runner](https://docs.github.com/actions/hosting-your-own-runners): той самий
workflow, лише `runs-on: self-hosted`, зате запити йдуть з вашої домашньої адреси.

**`немає __PRERENDERED_STATE__` при HTTP 200** — віддали капчу або змінилась розмітка.
Запустіть `probe`, щоб побачити, що саме прийшло.

**Прилетіло 25+ повідомлень і обрізалось** — запобіжник від флуду. Звузьте `max_price`
або додайте `include_keywords`.

**Бот мовчить** — перевірте, що ви натиснули `/start` у діалозі з ботом, і що
`TELEGRAM_CHAT_ID` — це число, а не `@username`.

**`Не вдалось під'єднатись до MongoDB`** — три звичні причини, у порядку
ймовірності: IP не в Network Access (потрібен `0.0.0.0/0` — раннер щоразу
інший); пароль у `MONGODB_URI` зі спецсимволами без percent-encoding; кластер
на паузі (Atlas паузить M0 після ~60 днів без звернень — при прогонах раз на
чверть години це не наш випадок).

**`--storage mongo, але MONGODB_URI порожній`** — секрет не доданий у GitHub
або рядок не потрапив у `.env` на домашній машині. Це навмисна помилка, а не
збій: див. таблицю `--storage` вище.

**Хмара й дім бачать різні оголошення** — майже напевно різні `MONGODB_URI`
(інший кластер або інша база в `MONGODB_DB`). Звірте обидва рядки посимвольно.

**Workflow сам вимкнувся** — GitHub глушить `schedule:` у публічних репо після
60 днів без активності. У нас `schedule:` немає взагалі (розклад дає
cron-job.org через `workflow_dispatch`), тож автовимкнення не загрожує — і те,
що стан більше не комітиться, цього не міняє.

## Про ввічливість і межі

Один запит на пошук раз на 15 хвилин — це мізер порівняно зі звичайним переглядом сайту, і
скрипт свідомо не паралелить запити й тримає паузи між пошуками. Не варто ставити cron на
кожну хвилину чи заводити сотню пошуків: це і вантажить чужий сайт, і швидше приведе до
блокування. Дані беруться лише публічні, з тієї ж сторінки, яку віддає браузер.
